## 1. 当前项目一句话

`@hbk/dsh-compaction-setmodel` 是已安装到 DSH **web profile** 的设置插件：在 Web GUI 的「上下文压缩」卡片中配置压缩专用模型与行为参数，并提供等价于 `/compact` 的「压缩上下文」按钮。

**本轮只修一件事：让卡片上显示的状态，等于 DSH 此刻的真实状态。**

## 2. 本轮问题定性（人工已确认）

### 2.1 功能层面：已经过关，不要再动

- 从第 54 轮起的多轮日志核查结论：**配置已生效、压缩已按预期执行**。
- 人工明确确认：**所有功能均已生效**。
- 因此本轮**不得**以"压缩可能没生效"为假设去做任何返工；压缩执行链路、参数语义、`compactNow` 调用方式、patch 写入/备份/回读/回滚全部保持现状。

### 2.2 插件层面：状态显示是错的，而且会一直错下去

**症状**：DSH 已经热重载完成、配置已经真的在生效，卡片上却仍显示"热重载中"这类中间态，且不会自行消失。

**实测证据**（0.2.0 安装后从 `GET /config` 取到的真实返回）：

| 字段 | 实际值 | 矛盾点 |
|---|---|---|
| `lastApplication.status` | `pending` | 声称"还没生效" |
| `lastApplication.pending` | `[]` | 没有任何一条待生效项 |
| `lastApplication.restartReason` | `null` | 也没有"必须重启"的理由 |
| `lastApplication.warnings` / `error` | `[]` / `null` | 既无警告也无错误 |
| `lastApplication.elapsedMs` | `180` | 确实跑过一次探测，且很快结束 |

"状态是 pending，但待生效清单为空、重启原因为空"——**这组返回本身自相矛盾**。该结论也确实误导了人工侧对"是否需要重启"的判断。

### 2.3 根因判断

**插件记录的是"上次保存那一刻拍下的照片"，而不是"此刻的镜子"。**

1. `lastApplication` 是内存里一次性写入的记录，产生于保存流程的中间阶段，之后没有任何代码回来把它更新为最终结论。
2. `GET /config` 直接回放这条旧记录，**不重新探测**；所以 DSH 后来是否完成重载、是否被重启、配置文件是否被改，插件一概不知。
3. 进程重启后内存记录丢失，状态来源只能靠默认值或旧缓存，更容易出现莫名的中间态。

结论：这不只是"文案不好看"，而是**状态机的归口错了**——判据应当是"想要的 vs 实际在跑的"现场比对，而不是"我记得上次怎样"。

## 3. 本轮目标

### 3.1 O1 — 状态由现场比对得出（核心）

每次对外提供状态时，用两侧值现场比对：

- **想要的（desired）**：磁盘 profile patch 中 `compaction-basic` 当前的实际配置，经规范化后得到。
- **实际在跑的（actual）**：运行时探测得到的 `compaction` 服务实到配置；取不到服务时退到 Loader 配置；两者都取不到则标记"不可用"。

判定表：

| 情形 | 对外状态 | 中文文案 |
|---|---|---|
| desired 与 actual 规范化后一致 | `applied` | 已生效 |
| 不一致，且官方明确回报非空 `pending` 或 `restartReason` | `restart-required` | 需重启 DSH 才能生效 |
| 不一致，但无重启依据、或探测不可用、或比对无法进行 | `unknown` | 无法确认（附原因） |
| 保存/应用阶段本身失败并留有错误 | `failed` | 应用失败（附真实错误链） |

硬性要求：

1. **禁止**再出现"中间态永久驻留"。`pending` 不作为长期对外状态；短窗口内定不下来就落 `unknown` 并写清原因，不得一直显示"热重载中"。
2. **禁止**自相矛盾返回：若计算结果显示"待生效"却既无 `pending` 项也无 `restartReason`，一律降级为 `unknown` 并注明"缺少重启依据"。
3. **禁止**无证据宣称已生效。判据只有"规范化后两侧一致"，并且必须在返回里标明依据来源。
4. 模式 A（`summarization*` 缺失/null/空串）的规范化规则沿用 0.2.0 已定语义：一律视为"未指定专用模型"；`retainTokens` 存在时 `retainRatio` 标为未知并跳过该字段比对。

### 3.2 O2 — 热重载跑完立刻落定最终结论

1. 保存流程发起官方热重载后，必须**等这次调用的结果回来**，再叠加一次现场探测，然后才写入状态记录——记录里存的必须是最终结论，不是中间值。
2. 设定有界收敛窗口（建议约 2 秒内 2–3 次探测，具体值在设计阶段定）。窗口内收敛即落 `applied` 或 `restart-required`；窗口结束仍未收敛则落 `unknown`，绝不延长为"继续等待"。

### 3.3 O3 — DSH 一有变动就主动刷新

1. 已订阅的配置重载/启动完成信号触发时，**立即作废缓存并重探**，不等下一次轮询。
2. 卡片打开或用户点「重新检测」时，**强制**现场探测（绕过缓存），拿到最新结论与依据。
3. 30 秒轮询降级为**兜底**，不再是唯一刷新手段。
4. 探测加**短缓存**（约 1 秒量级），避免轮询与手动刷新叠加时反复探测拖慢界面。

> 待设计阶段核实：DSH 是否提供"热重载已完成"的完成态事件。若有，优先挂该事件做到零延迟；若只有"配置变更"事件，则以"事件触发 + 有界重探 + 打开即探"组合达成同等效果。**不得**为了等事件而把状态卡在中间态。

### 3.4 O4 — 界面说人话，并显示证据

卡片状态区改为四态直说（已生效 / 需重启 / 无法确认 / 应用失败），并附一行诊断信息：

- 判断依据来源（运行时服务 / Loader 配置 / 不可用）
- **上次确认时间**（明确"这结论是几秒前确认的"，停了也看得出来）
- 重载版本号（DSH 侧配置重组计数）

同时清理误导性文案：不再使用会让用户以为"后台还在忙"的措辞描述已完成的动作。

### 3.5 O5 — 记录本插件按钮触发的最近一次压缩（附加，可整条删除）

- 只记录**本插件「压缩上下文」按钮**触发的最近一次结果：时间、成功/失败、历史项数或错误类别。
- 界面须如实标注"仅记录本插件按钮触发的压缩"，不暗示能看到其他会话或外部 `/compact` 的压缩。
- 该条为低风险附加项；若评审认为超出本轮范围，可整条删除，不影响 O1–O4 的验收。

## 5. 已确认的技术事实与实施约束

以下为 0.2.0 阶段已核实的事实，本轮直接沿用，不重新论证：

1. **运行时探测有三档来源**：`compaction` 服务 → Loader 配置 → 不可用。状态必须携带来源，取不到不得假装知道。
2. **热重载是进程内局部重挂载**，不是重启整个 DSH；官方提供 `runExclusive()` 与 `reconcileProfile()`，其结果含 `pending`、`restartReason`、`warnings`。
3. **非空 `pending` 的语义是"旧模块需重启后才被替换"**，因此它是"需重启"的依据，不是"再等等"的依据。
4. **配置重载/启动完成信号可订阅**，且已在 0.2.0 注册；本轮只是让它驱动"作废缓存 + 重探"。
5. **写盘成功与生效成功是两个结果**，必须分开报告；不得相互伪装。
6. **内存状态在进程重启后必然丢失**，因此对外状态必须可由"磁盘配置 + 现场探测"重建，不能依赖历史记录存活。
7. **`compaction/summary` 事件**可用于独立验证压缩实际路由（仅用于验收取证，不纳入插件运行时依赖）。

## 6. 验收标准

| 编号 | 场景 | 必须达到的结果 |
|---|---|---|
| D1 | 保存一份与运行值一致、无需变更路由的配置 | 保存返回里状态直接是"已生效"，不出现中间态驻留；附依据来源与确认时间 |
| D2 | 保存新专用 provider/model，热重载成功 | 短暂等待后状态为"已生效"；随后 `GET /config` 仍为"已生效"，**不会退回**"热重载中" |
| D3 | 热重载后人工观察 1 分钟不做任何操作 | 状态保持不变且不出现中间态；`上次确认时间`随轮询/刷新推进 |
| D4 | DSH 完全重启后首次打开卡片 | 不等保存、不需人工干预，即由现场比对得出正确状态（已生效/需重启），无"未知默认值"糊上去 |
| D5 | 手工把 patch 改回旧值（模拟外部修改） | 卡片在刷新后能反映"与运行值不一致"，并给出"无法确认"或"需重启"及原因，不谎报已生效 |
| D6 | 探测不可用（服务与 Loader 均取不到） | 状态为"无法确认"并注明原因；不得显示"已生效" |
| D7 | 出现"待生效但无 pending 项、无 restartReason"的自相矛盾数据 | 一律降级为"无法确认"并写明"缺少重启依据"；该矛盾不得传到界面 |
| D8 | 状态接口一致性 | `GET /config`、手动「重新检测」、保存返回三处的状态字段口径一致，含义相同 |
| R1 | 自动回归 | 既有 123 项检查保持通过；新增状态判定/刷新相关测试全部通过 |
| R2 | 配置安全 | patch diff 仍仅限 `compaction-basic` 目标字段；备份/回读/回滚有效，其他条目不受影响 |
| R3 | 压缩功能零回归 | 「压缩上下文」按钮与自动压缩行为与 0.2.0 一致；错误透明化与跟随文案不回退 |
| R4 | 性能与稳定 | 探测短缓存生效，轮询与手动刷新不造成可感知卡顿；无内存泄漏、无未捕获异常 |

> 状态判定类验收必须以**实际返回的字段值**为证据，不能只凭界面文字或 HTTP 200 判定通过。

## 10. 风险与对策

| 风险 | 对策 |
|---|---|
| 为让界面好看而谎报"已生效" | 判据固定为规范化比对；不满足即"无法确认"，并保留依据来源供核对 |
| 探测过于频繁拖慢界面 | 短缓存 + 事件驱动替代高频轮询；手动检测才强制穿透缓存 |
| 把"待生效"当长期状态，用户永远看不到结论 | 有界收敛窗口，窗口结束强制落 `unknown` 并写原因 |
| 进程重启后状态来源不明 | 状态可由"磁盘配置 + 现场探测"重建，不依赖内存历史 |
| 修状态时误伤压缩或写入链路 | 改动面严格限制在状态判定、刷新时序、接口字段、界面文案；R2/R3 强制回归 |
| 规范化规则不一致导致误报不一致 | 单一规范化函数、单一比对入口；模式 A 与 `retainTokens` 规则沿用 0.2.0 |
| 事件不存在导致刷新不及时 | 设计阶段先核实；不存在时以"事件 + 有界重探 + 打开即探"组合兜底 |
| 文档口径漂移 | 以 plan v7 为需求基线；design/code 必须同步，旧"回放记录"表述不得沿用 |
| 无关联改动混入交付 | 每个改动须能对应到 §6 某一验收项，否则不进入交付 |
